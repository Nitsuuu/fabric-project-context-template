# AI Workflow Rules — {{PROJECT_NAME}}

Direct instructions to Claude Code working on this project. Imperatives, not suggestions.

## Read before acting

Every Claude Code session opens by reading these files in order:

1. `project/context/project-overview.md` — what we're building and why
2. `project/context/architecture.md` — system structure and invariants
3. `project/context/data-conventions.md` — naming and schema rules
4. `project/context/code-standards.md` — coding conventions
5. `project/context/ai-workflow-rules.md` — this file
6. `project/context/progress-tracker.md` — current state

If any of these is stale or contradicts the current code, fix the doc in the same commit as the code change.

## Spec-driven development

This project uses a request-driven workflow. Work happens in units called REQs.

1. **Pick the next REQ from `project/requests/queue/`**. Read all five sections (Goal, Design, Implementation, Dependencies, Verify-when-done). If anything is unclear, ask before writing code.
2. **Move the REQ to `project/requests/working/`** when starting.
3. **Implement exactly what the REQ specifies.** No bonus refactors. No "while we're here" cleanups. No proactive new files.
4. **Update `project/context/progress-tracker.md`** when starting, when blocked, when done.
5. **Run the verify-when-done checklist.** If any item fails, the REQ stays in `working/`.
6. **Move the REQ to `project/requests/done/`** (or `blocked/`) only after verification passes.

## Scope discipline

- **One REQ at a time.** Do not pull a second REQ while another is in `working/`.
- **No speculative changes.** Do not add a function, parameter, or file because "we might need it."
- **No documentation files unless explicitly requested.** No `.md` files outside the directories specified in `project/context/architecture.md`.
- **Stay within system boundaries.** UI changes belong in one REQ; database changes belong in another. Do not mix.

## When something is missing or ambiguous

- **Missing requirement** — ask the user. Do not guess.
- **Ambiguous spec** — ask which interpretation applies. Do not pick the easier one.
- **Missing dependency** — list it as a blocker; do not silently install or import.
- **Architectural conflict** — flag it before implementing. The user updates `architecture.md` (with reasoning) and only then does the code change.

## Files that should not be modified without explicit instruction

- Any file under `~/.claude/` (global config and global standards).
- Lakehouse `.platform` files in `workspace-assets/{{LAKEHOUSE_PREFIX}}_*.Lakehouse/` — these contain GUIDs and are managed by Fabric git integration.
- `.github/workflows/*.yml` — promotion logic. Touch only with a dedicated REQ.
- Generated documentation (DBML, autogenerated diagrams).

## Verification checklist before declaring a REQ complete

- [ ] All items in the REQ's Verify-when-done section pass.
- [ ] No new `.count()` / `.collect()` inside loops.
- [ ] No hardcoded environment values (Variable Library / Key Vault used).
- [ ] No real secrets in any committed file.
- [ ] `etl_*` metadata columns present on Bronze/Silver writes.
- [ ] Pipeline is idempotent (re-run produces the same outputs).
- [ ] `progress-tracker.md` updated.
- [ ] Commit message follows the project's convention.
- [ ] If the REQ revealed a new pattern worth standardizing, the relevant `context/*.md` file is updated in the same commit.

## When AI gets stuck

Three rules, in order:

1. **Re-read the REQ.** Most "stuck" moments come from drifting from the spec. The spec is the source of truth, not the model's instinct.
2. **Re-read `architecture.md`** for the relevant boundary or invariant.
3. **Ask the user.** If neither (1) nor (2) clarifies, stop guessing. Ask one focused question.

Do not try the same approach repeatedly with minor variations. Two failed attempts is the signal to ask.
